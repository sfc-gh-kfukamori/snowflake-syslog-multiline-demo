# syslog形式マルチラインログ COPY INTO 取り込みデモ

## 概要

syslog形式で、ペイロード部分に改行コードを含むマルチラインログを、
Snowflakeの `COPY INTO` で取り込み、SQL内で1レコードに結合する方法のデモです。

## 前提条件

- 事前のデータ加工（Fluentd, Cribl等による正規化）は不可
- S3上の生syslogファイルをそのままSnowflakeに取り込む

## ファイル構成

```
syslog_multiline_demo/
├── README.md                    # 本ファイル
├── demo_syslog_multiline.sql    # デモSQLスクリプト
└── sample_syslog.log            # サンプルsyslogデータ
```

## アーキテクチャ

```
S3/Stage (生syslog .log)
  ↓ COPY INTO（1行=1レコードで丸呑み）
Bronze層 (RAW_LINE + FILE_ROW_NUMBER)
  ↓ SQL Window関数 + LISTAGG（ヘッダパターンで結合）
Silver層 (1レコード=1イベント)
  ↓ REGEXP_SUBSTR（フィールド抽出）
Gold層 (パース済み構造化ビュー)
```

## 実行手順（Snowsight）

### 1. Snowsight で Worksheet を開く

新規 SQL Worksheet を作成します。

### 2. Step 0〜2 を実行

`demo_syslog_multiline.sql` の Step 0〜2 を Worksheet に貼り付けて実行します。
データベース、スキーマ、ファイルフォーマット、内部ステージが作成されます。

### 3. サンプルデータをステージにアップロード

1. 左ペイン → **Data** → **Databases** → `SYSLOG_DEMO` → `RAW` → **Stages** → `SYSLOG_STAGE`
2. 右上の **「+ Files」** ボタンをクリック
3. `sample_syslog.log` を選択してアップロード

### 4. Step 4 以降を順に実行

Worksheet に戻り、Step 4 以降を順に実行していきます。

- **Step 4**: `COPY INTO` でBronze層に取り込み
- **Step 5**: Silver層（マルチライン結合）
- **Step 6**: Gold層（構造化ビュー）
- **Step 7**: 検証（期待値との比較）
- **Step 8**: 大規模負荷テスト（オプション、1000万行）

## サンプルデータの説明

`sample_syslog.log` には以下の4レコードが含まれています:

| # | 内容 | 物理行数 | 備考 |
|---|------|---------|------|
| 1 | ゾーンファイルロードエラー | 4行 | マルチライン（エラー詳細が複数行） |
| 2 | DNSクエリ通常ログ | 1行 | シングルライン |
| 3 | ゾーン転送失敗 | 4行 | マルチライン（転送エラー詳細） |
| 4 | MXクエリ通常ログ | 1行 | シングルライン |

合計10物理行 → 正しく処理されると **4論理レコード** になります。

## 技術的なポイント

### FILE_FORMAT の重要設定

| オプション | 値 | 理由 |
|---|---|---|
| `FIELD_DELIMITER` | `NONE` | 1行全体を単一VARCHARに |
| `ESCAPE_UNENCLOSED_FIELD` | `NONE` | 行末`\`による行結合を防止 |
| `SKIP_BLANK_LINES` | `TRUE` | 空行スキップ |

### RLIKE/REGEXP_LIKE の注意点

Snowflakeの `RLIKE` / `REGEXP_LIKE` は **全体マッチ** がデフォルトです。
部分マッチのつもりで使う場合は末尾に `.*` を付ける必要があります:

```sql
-- NG: マッチしない（全体マッチのため）
raw_line RLIKE '^<[0-9]+>[A-Za-z]{3}\\s+[0-9]+\\s+[0-9]{2}:[0-9]{2}:[0-9]{2}\\s+\\S+'

-- OK: 末尾に .* を付けて全体を覆う
raw_line RLIKE '^<[0-9]+>[A-Za-z]{3}\\s+[0-9]+\\s+[0-9]{2}:[0-9]{2}:[0-9]{2}\\s+\\S+.*'
```

### LISTAGGの制限

- 結果文字列の最大長はデフォルト16MB
- 1イベントが極端に長い場合は `LEFT(merged_log, 65536)` 等で制限

## パフォーマンス実測結果（1000万行テスト）

Step 8 の大規模負荷テストの実測値です。

### テスト条件

| 項目 | 値 |
|---|---|
| Bronze層行数 | 10,000,000行 |
| Silver層レコード数 | 6,000,000レコード |
| マルチライン(3行)レコード | 2,000,000件（33%） |
| シングルラインレコード | 4,000,000件（67%） |
| ファイル数（PARTITION数） | 50ファイル（各20万行） |

### ウェアハウスサイズ別パフォーマンス

| サイズ | 実行時間 | Credit/時 | 1回あたりコスト概算 |
|---|---|---|---|
| X-Small | 8.2秒 | 1 | ~$0.006 |
| Small | 8.2秒 | 2 | ~$0.012 |
| Medium | 5.1秒 | 4 | ~$0.016 |

### 考察

- **XSで8秒** は1日1回バッチ処理として十分実用的
- XS→Smallで変化なし: パーティション数(50)に対してSmall(2ノード)では並列化メリットが限定的
- Mediumで約40%短縮: パーティション数に見合うクラスタ数で並列処理が効き始める
- スピル（メモリ溢れ）は未発生: 1パーティション20万行程度はメモリ内処理可能

### スケーラビリティの注意点

| 状況 | 影響 | 対策 |
|---|---|---|
| ファイル数が多い（100+） | 良好（自然に並列化） | ウェアハウスをスケールアップ |
| 1ファイルが巨大（数百万行） | パーティション偏りで性能低下 | ファイルを分割して投入 |
| 1イベントが極端に長い | LISTAGGの16MB上限に抵触 | LEFT(merged_log, 65536) で制限 |

### 投入パターン別の運用推奨

| 投入パターン | 推奨方式 |
|---|---|
| Snowpipe（継続的少量投入） | Stream + Task で差分処理 |
| バッチ（1日1回大量投入） | COPY INTO直後にCTASでSilver層作成 |
| バッチ（1時間ごと中規模） | 日付/バッチIDフィルタでINSERT |

**注意**: バッチ1回投入の場合、Stream + Taskにしても差分=全量なのでメリットはありません。
CTASまたはバッチIDフィルタによるINSERTの方がシンプルです。
